    REGLES METIER (Sprint 7)
        - Une reservation devient divisible (split passagers) si aucun vehicule unique ne peut absorber tous les passagers restants.
        - Priorite de traitement des reservations : nbPassager DESC.
        - Pour une reservation en cours, on traite TOUTES ses divisions/sous-parties avant de passer a la reservation suivante.
        - Resolution explicite du tri vehicule :
          1) On recupere/ordonne d'abord les vehicules en DESC (capacite) depuis la base
          2) Pendant le traitement d'assignation, on choisit le vehicule "plus proche" du besoin restant
          3) Tie-breakers ensuite : nb trajets min, diesel, random
        - Les vehicules disponibles sont tries, et le choix se fait sur la capacite la plus proche du besoin restant,
          puis tie-breakers : nb trajets min, diesel, random.
        - Si un vehicule est entame (places restantes), il doit etre rempli prioritairement avec des reservations compatibles
          en parcourant la liste vers le bas.
        - Les passagers restants non assignables d'une reservation sont reportes au regroupement suivant.
        - Temps d'attente / regroupement reste identique aux sprints precedents.
        - La logique trajet existante reste valable ; seul le mode d'assignation evolue.

    TACHE 2 : Nouveau mode d’assignation Sprint 7 (split + traitement par reste + vehicules entames prioritaires)
        Responsable :
            ETU003324

        Metier :
            - Dans chaque groupe (tranche), traiter les reservations par nbPassager DESC
            - Pour une reservation en cours :
                * Calculer passagers_restants
                * Tant que passagers_restants > 0 :
                    - Si existe un vehicule unique disponible capable de prendre passagers_restants :
                        => assigner en 1 fois (pas de split)
                    - Sinon :
                        => la reservation devient divisible :
                           assigner un maximum possible en choisissant un vehicule disponible selon la regle "plus proche"
                           du besoin restant (et tie-breakers)
            - Prioriser le remplissage des vehicules entames :
                * Si un vehicule a des places restantes sur le groupe courant, le remplir en premier
                  en parcourant la liste vers le bas (reservations compatibles)
            - Si apres tentative il reste des passagers non assignables :
                * Reporter ces passagers au regroupement (groupe) suivant (meme run de planification)

        Resolution du choix vehicule (obligatoire) :
            1) Les vehicules sont recuperes depuis la DB en DESC capacite (base order)
               (voir [backoffice_framework/src/com/back/repository/VehiculeRepository.java](backoffice_framework/src/com/back/repository/VehiculeRepository.java))
            2) Parmi les vehicules DISPONIBLES, choisir la capacite "plus proche" du besoin restant
               (interpretation simple : min(capacite >= besoin))
            3) Tie-breakers :
                - nb trajets min (nombre de voyages deja crees pour ce vehicule sur la date)
                  (deja accessible via VehiculePlanDTO.getNombreVoyages())
                - Diesel prioritaire
                - Random si encore egalite (random explicite, pas juste return 0)

        Regles de gestion :
            - La disponibilite (heure_retour <= heure_depart_groupe) est verifiee AVANT le choix (comme Sprint 6)
            - Temps d’attente/tranches : inchangé (grouperParTrancheAttente)
            - TrajetCalculator et calcul d'heure_retour : inchangés (on reutilise le calcul aller+retour existant)

        Livrables (zone de code) :
            - Refactor/ajouts dans
              [backoffice_framework/src/com/back/planification/PlanificationService.java](backoffice_framework/src/com/back/planification/PlanificationService.java)
              (nouvelle boucle d’assignation par reservation + gestion du split + remplissage prioritaire vehicules entames)
            - Eventuel ajustement/extension DTO si necessaire pour afficher les sous-parties (ex: passagers assignes par partie)
              dans
              [backoffice_framework/src/com/back/planification/VoyageDTO.java](backoffice_framework/src/com/back/planification/VoyageDTO.java)
              et/ou [backoffice_framework/src/com/back/planification/VehiculePlanDTO.java](backoffice_framework/src/com/back/planification/VehiculePlanDTO.java)
